# Selective upstream routing

This map recommends optional installed skills. It is not an installer and does not cause every upstream to load. Check the host inventory and exact skill body/dependencies before invoking it. If unavailable, follow the relevant oxk playbook and disclose the missing capability only when it affects the task.

| Need | Candidate | How to use |
| --- | --- | --- |
| Product/domain uncertainty | Matt grilling, grill-with-docs, domain-modeling | Resolve consequential questions; keep wrappers' dependencies |
| Difficult repository investigation | HumanLayer research/plan/implement method | Evidence with paths, explicit plan and verified phases; adapt host-specific tooling |
| Execution/orchestration | pstack poteto-mode and relevant playbooks | Adapt worker/model/provider/continuation references to the host; TASK delivery rights win |
| New visual direction | Anthropic frontend-design | Establish coherent visual choices and states |
| Component/interaction craft | Emil emil-design-eng | Apply the chosen direction and real interaction details |
| Unsettled UI | Emil prototype | Isolated alternatives and user selection before promotion |
| Motion | Emil animate / review-animations | Purposeful implementation and targeted animation review |
| Mobile/native-feeling UX | Emil mobile-native; optional apple-design | Load when the product/direction calls for it |
| Missing UI capability | Emil pick-ui-library | Compare only after checking existing dependencies |
| Bug mechanism | Matt diagnosing-bugs or pstack bug/TDD path | Reproduction and useful regression evidence |
| Domain/module boundary uncertainty | Matt codebase-design; pstack architecture methods | Scale investigation to the decision, preserve a settled structure |
| Complexity control | Ponytail | Apply during scoped implementation/cleanup; requirements govern simplification |

Matt skills are useful for stack-independent decisions as well as TS projects. Keep one preferred entry point per job, not every similarly named command. A wrapper such as grill-with-docs may require other installed skills; removing dependencies breaks it.

Names such as `prototype`, `tdd` and `teach` can collide across sources. Check pi startup diagnostics and explicit skill identity; first-discovered collisions can select the wrong body. Use an intentional alias/adapter with rewritten internal references when maintaining a renamed copy. Do not merely rename a folder and assume dependencies still resolve.

Ponytail's level names and behavior are version-dependent; record the installed version and actual available commands. FaSearch policy takes precedence: `full` for implementation/fixes, `lite` for review, `off` for grilling when available. Set and verify it in the live Pi session. Preserve purposeful UI details; raise a tradeoff when simplification would remove them. Complexity review supplements the independent correctness/spec review. Preserve documented tradeoffs and necessary comments despite generic upstream rules.

The curated reference SHAs in upstreams.lock.json record source provenance at authoring time. They do not prove host compatibility or install a dependency. pstack's Cursor Task/model/cloud/loop references need a pi adapter; HumanLayer prompts likewise need path/tool adaptation. Community pi ports should be evaluated on a scoped task before enabling unattended work. Check licenses before vendoring upstream files.
